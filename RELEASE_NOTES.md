# ZMK Vision v2.11.1 — Fix camera “не подключена” when VLC works

## Проблема

Камера отлично работает в VLC, но на сайте — «не подключена» (offline, без кадров). После того, как авторизация токена была исправлена, остались две причины именно такого поведения:

1. **Транспорт RTSP.** Воркер открывал поток только по TCP (`rtsp_transport;tcp`). Если камера/путь не поддерживает TCP-interleaved (или OpenCV-бэкенд его не тянет) — поток вообще не открывается → «не подключена». VLC при этом может идти по UDP и работать.
2. **`CAP_PROP_BUFFERSIZE=1` на FFmpeg** — опасная настройка, дающая чёрный/застрявший кадр на ряде камер.
3. **Сам воркер не запущен** (профиль `inference` не поднят) — камера молча «не подключена» без объяснений.

## Решение

### Авто-выбор транспорта (auto-fallback)
- `RTSP_TRANSPORT` теперь **`auto`** по умолчанию: пробует **TCP**, при неудаче переключается на **UDP** (и чередует при обрыве). Это лечит «в VLC работает — у нас нет».
- Можно зафиксировать: `RTSP_TRANSPORT=tcp` или `=udp`.
- Убран принудительный `CAP_PROP_BUFFERSIZE=1`; добавлена опциональная `RTSP_BUFFER_SIZE` (пусто = по умолчанию) для случая чёрного/замерзшего кадра.

### Понятная диагностика
- В **Диагностике** (панель) теперь явный баннер: либо «Инференс-воркер активен», либо «Инференс-воркер не даёт кадры — запустите профиль inference и проверьте логи».
- `/api/capabilities` и `/api/system-health` сообщают, работает ли инференс-воркер (по свежести снимков), а не только наличие модели.
- Воркер логирует, каким транспортом открыл/не открыл поток и сколько было попыток.

### Какие параметры теперь смотреть/менять (в `.env`)
```env
RTSP_TRANSPORT=auto        # auto | tcp | udp  (auto — рекомендуется)
RTSP_BUFFER_SIZE=          # опционально, напр. 5 для чёрного/застрявшего кадра
OFFLINE_AFTER_FRAMES=3     # сколько неудачных кадров = «офлайн»
RTSP_RECONNECT_SECONDS=5
```

## Проверки
- Backend **59/59** (добавлены тесты `inference_worker`/`fresh_snapshots` в capabilities), установщики/updater/worker **28/28** (добавлен тест авто-перебора транспорта и его логики), Telegram 3/3, MAX 3/3.
- Ruff, Bandit (прод+updater), tsc/lint, `npm audit` (0), pip-audit (0), shell, compose, `git diff --check` — чисто.
- Логика покрыта юнит-тестами на fake-каптуре; в песочнице нет реальной RTSP-камеры, поэтому реальный декодинг проверяется на вашей машине по логам.

## Как применить и проверить

```bash
# пересобрать и поднять всё (важно пересобрать воркер!)
docker compose up -d --build --remove-orphans
docker compose --profile inference up -d --build
# смотреть логи воркера:
docker compose --profile inference logs --tail=150 inference-worker
```

Если после этого в логе появится `OPENED via tcp` / `OPENED via udp` — поток открыт, камера должна показать кадры. Если `FAILED to open via ...` — проверьте RTSP URL, учётные данные, сеть (или попробуйте `RTSP_TRANSPORT=udp`). Пришлите этот лог — разберём, что конкретно не так с вашей камерой.
