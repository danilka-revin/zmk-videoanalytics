# Регистрация модели в ZMK Vision

Гайд основан на фактической логике `POST /api/models/upload`, `POST /api/models`, `POST /api/models/{name}/activate`, `GET /api/internal/active-model` и кода inference-воркера.

## Что такое «модель» в системе

Модель — это **готовая (уже обученная/экспортированная) нейросеть**, которую inference-воркер загружает и гоняет по RTSP-кадрам, а полученные детекции превращает в события. Регистрация — это просто запись в реестр `model_registry` с указанием, **откуда взять файл** и **какие у него метрики**. Сам файл лежит на диске (или в Docker-томе `model-data`), а не «в базе».

> Система не обучает модель в момент регистрации. Обучение — отдельный процесс (training worker). Регистрация лишь добавляет артефакт в реестр и делает его кандидатом на активацию.

## Как открыть форму

Панель → **Модели** → кнопка **«Зарегистрировать модель»**.

## Загрузка файла с компьютера — рекомендуемый путь

1. В блоке **«Файл модели с компьютера»** нажмите **«Выбрать файл модели»**.
2. Выберите готовый артефакт: `.onnx` для ONNX, `.engine` / `.plan` / `.trt` для TensorRT либо `.pt` / `.pth` для PyTorch.
3. Проверьте автоматически предложенные имя и формат, укажите реальные метрики Precision и Recall.
4. Нажмите **«Загрузить и зарегистрировать»**.

API потоково записывает файл в общий Docker volume `model-data` (`/models` внутри API и inference-worker), создаёт безопасный путь `file:///models/<имя>.<расширение>`, вычисляет SHA-256 и сразу добавляет запись в реестр. В браузер или базу данных сам файл не копируется. Лимит по умолчанию — **2 ГБ** на файл; его можно уменьшить переменной `MODEL_UPLOAD_MAX_BYTES`.

> Загружайте только доверенные артефакты. Это особенно важно для `.pt` / `.pth`: PyTorch-загрузчики могут выполнять небезопасный код из непроверенных файлов.

## Поля формы и что они значат

| Поле | Ограничение | Смысл |
|---|---|---|
| **Имя** | 2–120 симв., только `[A-Za-z0-9._-]` | Уникальный идентификатор. Используется в команде активации. Уже существующее имя → `409`. |
| **Формат** | `ONNX`, `ONNX FP16`, `TensorRT`, `TensorRT FP16`, `PyTorch` | Подпись типа артефакта. Влияет на то, как его загрузит воркер. |
| **Файл модели** | `.onnx`, `.engine` / `.plan` / `.trt`, `.pt` / `.pth` | Основной путь: выбрать файл с компьютера. Сервер сам сохраняет его в `model-data`. |
| **Artifact URI** | ≤1000 симв., только расширенный режим | Нужен лишь когда файл уже вручную лежит на сервере; указывается с префиксом `file://`. |
| **Precision, %** | 0–100 | Метрика валидации. **Обязательна для активации.** |
| **Recall, %** | 0–100 | Метрика валидации. **Обязательна для активации.** |
| **SHA-256 checksum** | автоматически при upload; hex, ≤128 симв. в расширенном режиме | Воркер проверяет сумму при загрузке и **откажет** при несовпадении. |
| Source | заполняется системой для upload | Для локального файла будет `upload:<имя файла>`; авто-обучение проставляет `camera:...` / `dataset:...`. |

## Расширенный режим: как правильно указать Artifact URI

Это нужно только если файл уже был размещён на сервере вручную. Воркер делает `artifact_uri.removeprefix("file://")` и открывает получившийся путь, поэтому:

- Внутри Docker-контейнера inference-воркера том `model-data` смонтирован как **`/models`**. Поэтому путь к файлу в томе — `file:///models/имя.файл`.
- Для моделей, **полученных автообучением**, training worker сам кладёт файл в `/models/<target_name>.onnx` и регистрирует модель с правильным URI — здесь руками ничего заполнять не надо.
- Для **внешних** моделей, загружаемых через панель, вручную класть файл в volume и указывать путь не нужно — это делает `POST /api/models/upload`.
- В расширенном режиме можно положить файл в `model-data` под `/models/` и указать `file:///models/<имя>.onnx`, либо абсолютный путь **внутри контейнера** воркера.

Если файл по указанному пути отсутствует, воркер при запуске/ping модели выдаст ошибку `Model artifact not found: <path>`.

## Проверка и привязка классов (важно для качества)

Inference-воркер **фильтрует** детекции и превращает в события только классы из фиксированного списка:

```
no_helmet  no_vest  phone_usage  smoking  restricted_zone  immobility
```

Для обычных safety-классов нужны имена из списка выше. Но для PPE есть специальная совместимость: `Human`/`person`, `Helmet`/`hardhat`/`hat` и `No-Helmet`/`nohat`/`no_helmet` нормализуются worker-ом, а событие `no_helmet` привязывается к найденному человеку.

На live-камере рисуются **все реальные классы** вашей модели, в том числе нестандартные (`forklift`, `car`, свои классы). При этом события безопасности создаются только для совместимых классов из списка выше — модель с произвольными классами не начнёт генерировать ложные нарушения.

**Важно:** стандартная COCO-модель с одним только `person` всё равно **не создаёт** нарушение — в ней нет класса каски. Используйте готовый PPE-пресет или модель, у которой есть как минимум `person` и `helmet` (либо явный `no_helmet`), затем проверьте её на своих кадрах. Подробнее: [`PPE_HELMET_BASELINE_RU.md`](PPE_HELMET_BASELINE_RU.md).

## Порог активации (что может помешать)

Активировать модель можно, только если она одновременно:
1. `status = ready` (регистрация проставляет `ready` сразу);
2. заданы **и** precision, **и** recall (не `null`);
3. `precision >= min_model_precision` и `recall >= min_model_recall`.

Минимальные пороги по умолчанию: **Precision ≥ 90**, **Recall ≥ 85** (настраиваются в Настройках → AI-модель, ключи `min_model_precision` / `min_model_recall`).

Если метрики ниже — при нажатии «Горячая замена» будет `409: Метрики модели ниже минимально допустимых`.

## Как активировать

- **Из панели:** Модели → карточка модели → кнопка **«Горячая замена»** (если модель активна — кнопка «Используется»).
- **Из бота (admin):** `/switch_model <имя>` (Telegram или MAX).
- **Через API:** `POST /api/models/{name}/activate`.

Активация — атомарная горячая замена **без остановки API**: переключается указатель `active_model`, старый `previous_model` логируется в `model_manager`. `GET /api/models/active/health` вернёт `healthy: true/false` и требования, а `GET /api/dashboard` покажет активную модель и её метрики.

Карточка активной модели в панели дополнительно показывает реальный статус inference-worker: **загружается**, **загружена**, **worker не на связи** или точную безопасную ошибку загрузки. Поэтому выбор в реестре не будет выдаваться за работающую модель, если файл/формат несовместимы. Активную модель также можно удалить одной подтверждённой кнопкой: аналитика остановится, затем запись и загруженный файл будут удалены.

Для любой готовой модели доступна кнопка **«Тест на камере»**. Она запускает реальные рамки на live-камере даже при недостаточных или ещё непроверенных метриках, но явно помечает режим как тестовый, не отправляет production-события/тревоги и не отменяет quality gate для обычной production-активации.

Для очистки реестра нажмите **«Выбрать для удаления»** в правой части раздела «Модели», отметьте несколько карточек и подтвердите операцию. Активные модели будут остановлены перед удалением; модели с запущенным обучением сохранятся, а панель покажет причину.

> Простая проверка: активация идемпотентна — если модель уже активна, повторный запрос вернёт `hot_swap=false, idempotent=true` и ничего не сломает.

## Периодическая проверка целостности

- `GET /api/models/active/health` — вернёт `healthy` (сравнение метрик с минимальными порогами) и `last_inference`.
- Если у модели задан checksum — воркер сверяет SHA256 файла **при каждой загрузке модели**. Несовпадение → `Model checksum mismatch`, модель не загрузится. Это защита от подмены артефакта.

## Примеры

### Пример 1: модель с компьютера через панель

```text
Выбранный файл: factory-ppe.onnx
Имя:            siz-guard-v2
Формат:          ONNX
Precision:        92.4
Recall:           87.1

Создаётся автоматически:
Artifact URI:     file:///models/siz-guard-v2.onnx
SHA-256:          <вычислен сервером>
```

### Пример 2: модель, полученная автообучением

Её регистрировать вручную **не нужно** — training worker сделает это сам и проставит правильные `artifact_uri`, `precision`, `recall` и source. В реестре она появится автоматически.

### Пример 3: Python (API)

```bash
curl -X POST http://localhost:8000/api/models \
  -H 'Content-Type: application/json' \
  -d '{"name":"siz-guard-v2","format":"ONNX","precision":92.4,"recall":87.1,"source":"external","artifact_uri":"file:///models/siz-guard-v2.onnx","checksum":"3a9f..."}'
```

```bash
# Загрузка файла через API (аналог кнопки в панели)
curl -X POST 'http://localhost:8000/api/models/upload?name=siz-guard-v2&format=ONNX&precision=92.4&recall=87.1&filename=siz-guard-v2.onnx' \
  -H 'Content-Type: application/octet-stream' \
  --data-binary '@siz-guard-v2.onnx'

# активация
curl -X POST http://localhost:8000/api/models/siz-guard-v2/activate
```

## Если что-то не так — симптомы

| Симптом | Причина / проверка |
|---|---|
| Панель: «Модели не зарегистрированы» | Реестр пуст — зарегистрируйте модель (или запустите обучение). |
| Бот: кнопка обучения недоступна | Worker (`training`) не запущен / `TRAINING_WORKER_URL` не задан. |
| События не создаются, хотя детекции идут | Имена классов не совпадают с `no_helmet / no_vest / phone_usage / smoking / restricted_zone / immobility`. |
| `413: Модель слишком большая` | Файл превысил `MODEL_UPLOAD_MAX_BYTES`; увеличьте лимит только при достаточном месте на диске или используйте меньший артефакт. |
| `422: Для формата … выберите файл` | Расширение не соответствует выбранному формату: ONNX `.onnx`, TensorRT `.engine/.plan/.trt`, PyTorch `.pt/.pth`. |
| `Model artifact not found` | Неверный ручной `artifact_uri` (файла нет по пути внутри контейнера). При загрузке через панель путь создаётся автоматически. |
| `Model checksum mismatch` | Файл изменён после регистрации — загрузите артефакт заново или обновите checksum в расширенном режиме. |
| `409: Метрики модели ниже минимально допустимых` | Поднимите precision/recall или снизьте пороги в Настройках → AI-модель. |
| Ошибки воркера | `docker compose --profile inference logs --tail=100 inference-worker` |
